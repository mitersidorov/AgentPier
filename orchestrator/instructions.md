# AgentPier orchestration rules

## Instruction priority

Applicable system and safety constraints take precedence. Otherwise, a direct user instruction takes priority over repository instructions, agent-profile instructions, skills, and ordinary orchestration conventions when they conflict. Record the instruction and honor its explicit scope.

1. Preserve the original user request verbatim and resolve the registered project and relevant applications/repositories.
2. Before analysis or execution, read the canonical orchestration instructions, the relevant repository instructions, confirmed project memory, the relevant stack profile and the skills nested under that profile. Record versions or content hashes used for each session.
3. Start fresh app-server threads for analysis with `sandbox: read-only`; do not reuse existing threads. Persist session/thread IDs and stream all messages/events.
4. Combine analysis results into a complete draft plan and publish the full plan to the user in chat. Never run implementation until the user explicitly confirms that plan; store the exact confirmation and approved plan separately from drafts.
5. Decompose only approved plans into tasks with explicit dependencies, profile and repository assignments. Schedule independent work concurrently and wait for dependencies before downstream work.
6. Before plan approval, record an explicit `targetBranch` for every executable step/repository. If the user has not selected a branch, ask which branch to use and wait; do not approve or execute a plan with a missing branch, and never infer, generate, or create a branch automatically. If the user selects the current branch, use it without switching. Preserve unrelated working-tree changes; if the selected branch is not checked out, stop and ask the user to check it out before retrying rather than switching on their behalf.
7. Give each new session the current contract, relevant project memory, versioned instructions and skills. After an upstream contract changes, refresh downstream prompts before starting dependent work.
8. Save status transitions, timestamps, messages, questions, output, tests, errors and final summaries. Cancellation interrupts active turns but never deletes prior task data.
9. Return affected repositories, branches, changes, checks and unresolved decisions. Apply the Git and release scope rules below; implementation approval alone never authorizes publication.
10. Back up MySQL before migrations classified as destructive, after agreed milestones and on the configured schedule. Record backup outcomes without secrets; verify restore in an isolated database.

## Runtime boundaries

- The Manager, read-only dashboard, and MySQL run in Docker Compose. The Codex app-server and project checkouts/Git run on the Mac host, outside Docker; send absolute Mac paths through the app-server protocol and never mount user checkouts into Manager.
- MCP clients connect directly to Manager's `/mcp` endpoint (or through a separately configured tunnel). The dashboard is read-only presentation and never proxies MCP writes.
- Describe client GUI setup only when verified for the actual client/version. Prefer directing users to the client's current setup documentation rather than asserting unverified menu paths or capabilities.
- Report live app-server model/session and GUI checks as unverified when sandbox or connectivity prevents exercising them; do not claim a successful IDE launch without observing it.

## Local Git and release scope

- An agent may invoke installed local `git` and `gh` programs through its available host execution tools. A dedicated GitHub MCP or a Manager GitHub client is not a prerequisite. Use the registered checkout's absolute path; first verify the current branch, working tree, intended remote, and available tooling. Read-only inspection does not authorize mutations.
- Record explicit user scope for each operation: commit (repository, selected changes and target branch), push (remote and branch/ref), PR (head/base repository and branch, create/update), review (local assessment versus submitting a comment, approval, or change request), and merge (specific PR, target and method). A local diff review is read-only; submitting a GitHub review is a remote write. One user instruction may explicitly authorize multiple operations; no additional message is needed for an already explicit scope. A request to implement, commit, push, open a PR, review, or merge does not implicitly authorize the other operations. Clarify missing release targets before writing.
- Run only the authorized operations, in dependency order, with the relevant checks. Review the exact staged diff before a commit and include only approved changes; do not use blanket staging on a dirty checkout. Preserve preexisting staged, unstaged, and untracked work. Reports remain ignored and must not be staged or committed. Force-push, destructive cleanup, tag/release publication, and branch deletion require their own explicit scope; never infer them from merge or release wording.
- Keep the user-selected `targetBranch`. Never infer, create, or switch branches as part of implementation. If it is not checked out, stop and ask the user to check it out. A direct request for branch management is separate scope, not permission to silently change an approved task's branch; Manager currently offers no managed branch-switch workflow.
- Direct user instructions override conflicting repository/profile/skill conventions within their explicit scope, but not system, safety, tool permissions, or sandbox restrictions. Do not reject an explicitly scoped Git/gh action solely because the MVP has no GitHub client. Conversely, do not treat user authorization as evidence that the runtime can perform it. If unavailable or blocked, report the exact operation and sanitized failure; request an appropriate user action instead of bypassing restrictions.
- Use existing host credential helpers, SSH agents, or authenticated CLI configuration when permitted. Never ask for tokens in chat, embed credentials in commands/remote URLs, read or print credential stores, or put secrets in prompts, records, events, logs, or reports. Do not run token-display commands. Keep authentication checks/output minimal and sanitized; do not enable credential-bearing tracing. Missing authentication requires user setup outside task records, not fallback credentials.
- Record actual commands, sanitized results, commit IDs, PR/review links, and merge outcomes only when observed. Never claim that a local commit was pushed, a PR was reviewed remotely, or a merge succeeded without verifying that specific result. Report incomplete/blocked actions separately.

## Current capability boundaries and verification

- Manager stores repository remote URLs as metadata. `apps/manager/src/integrations/github/` is a documentation boundary, not an executable GitHub client. Manager performs local branch/status/diff inspection through the Mac app-server; it has no automated commit, push, PR, review, merge, clone, or release API. Optional external tools are separate capabilities, not Manager features.
- Managed execution requires the selected branch to be checked out. Only a non-empty, validated `releaseOperations` array on a persisted, explicitly user-approved plan step replaces the default no-commit/no-push/no-PR/no-submitted-review/no-merge handoff. Free-text requests, messages, draft plans and implementation approval without typed scope do not enable publication. Each typed operation records explicit targets within that step's registered repository and `targetBranch`; all other operations remain forbidden. This scoped handoff takes precedence over default no-publish profile wording, never over actual tool permissions.
- Ordinary analysis/execution turns and host `command/exec` keep network disabled and receive no additional Git writable root. Release execution turns and explicitly scoped host commands request network access and workspace writes only to the registered checkout plus its safely host-resolved Git metadata directory; `approvalPolicy: never` remains unchanged. Git paths cannot be supplied by callers. Resolution verifies the checkout root and canonical containment; external/shared worktree Git directories fail closed. These permissions are not command-level enforcement of individual Git operations and do not implement a GitHub client, bypass authentication, or prove effective host access. Continued turns inherit the accepted scope and cannot broaden it through messages.
- Manager's short status/diff summaries are not a full release inventory. Before an authorized commit/release, inspect `git status --porcelain=v1 --untracked-files=all`, staged and unstaged diffs, and relevant untracked files without exposing secrets. Record exclusions and do not discard unrelated work.
- Instruction-only changes require conflict/applicability review across canonical rules, repository instructions, both profiles and affected skills, an English-only scan of changed instructions, and `git diff --check`. They do not require unrelated application tests, builds, browser, MCP, WebSocket, or Docker checks. Runtime orchestration changes still require real MCP/app-server verification; report every unexercised integration explicitly. Historical workflow diagrams and passing mocks are not evidence of publishing infrastructure.
